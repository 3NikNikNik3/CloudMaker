# CloudMaker

[Docker](https://www.docker.com/)

Python, [FastAPI](https://github.com/fastapi/fastapi)

[QEMU](https://github.com/qemu/qemu)

Для образа диска по умолчанию: [Alpine](https://alpinelinux.org/)

# О проекте

CloudMaker - проект, сделанный для выполнения 1-ого задание на спецсеминаре

А если по делу: он позволяет запустить внутри docker-контейнера множество виртуальных машин и управлять ими через http api

Этот docker-контейнер подготавливался для Linux

# Инструкция запуска, тестирования и проверки

## Запуск

Сперва Вам нужно скачать сам контейнер:

	git --clone github.com/3NikNikNik3/CloudMaker.git

Или с https://github.com/3NikNikNik3/CloudMaker/archive/refs/heads/main.zip

После распаковать образ диска (он слишком велик без сжатия)

	cd data/
	tar -xzf disk.qcow2.tar.gz
	cd ../

Для запуска нужен `docker` и `docker.compose`

Чтобы запустить:

	docker compose up --build

### О настройках запуска

Есть некоторые компоненты, которые можно настроить через `compose.yaml`:
 - порт для http api: по умолчанию 8000
 - порт для подключения через ssh: по умолчанию 9000
 - папка для хранения данных меж запусками: по умолчанию `data/`
 - сколько оперативной памяти (в мибибайтах) и ядер cpu использовать максимально: по умолчанию 6144 и 4

В последующих примерах я буду исходить из настроек по умолчанию

## О взаимодействии с приложением

Большая часть взаимодействия с приложением через http api

Посмотреть и отправить все доступные http api запросы можно через страницу `/docs`, автоматически созданную `FastApi`

Но также можно воспользоваться и другими средствами. В терминале я рекомендую `curl`

Собственно, когда я буду описывать запрос, он будет в таком виде:

	/url method
	{
		key = value,
	...
	}

имея в виду - отправить на `/url` запрос типа `method` с данными `...`. Через `curl` это будет выглядеть так:

	curl localhost:8000/<url> -X <methods> -d '<key=value&>'

Я буду вместо `value` подставлять конкретные примеры, чтобы получить последовательность запросов, но вместо них можно подставлять и другие значение того же типа, логически подходящие

Исключения будут обговариваться "на месте"

## Тестирование управление VM

### Создание

Чтобы создать виртуальную машину нужно:

	/vm post
	{
		mem = "1G",
		cpu = 1,
		disk = "disk.qcow2"
	}

Это создаст виртуальную машину с 1Гиб оперативной памяти и 1 ядром cpu с подключённым `disk.qcow2` (он предустановлен)

Должно вернуть {"id": 0} - номер созданной ВМ

Нельзя запустить ВМ с диском, который уже используется! И ещё есть лимит на RAM и CPU

### Список

Чтобы получить список запущенных ВМ нужно:

	/vm get
	{
	}

Вы получите примерно

	{
		"arr": [
			"id": 0,
			"mem": 1024,
			"cpu": 1,
			"disk": "disk.qcow2"
		],
		"use_mem": 1024,
		"use_cpu": 1
	}

`arr` - собственно список, а `use_mem` и `use_cpu` - выделенные ВМ ресурсы

### Удаление
Чтобы остановить ВМ:

	/vm delete
	{
		id = 0,
		kill = false
	}

Если `kill = false`, программа "попросит" ВМ остановиться (`SIGINT`), иначе она её жёстко остановит (`SIGKILL`). Последнее рекомендуется использовать лишь в крайних случаях!

## Тестирование подключения ssh

Чтобы виртуальные машины были ося4заемые, к ним можно подключиться через `ssh`

Поскольку виртуальных машин может быть много, а порт выбирается статически реализована такая система - Вы подключаетесь через `9000` порт, а внутри контейнера есть простой прокси `socat`, который перенаправляет все запросы к нужной ВМ. И через http api можно настроить к какой виртуальной машине сейчас стоит перенаправление

Собственно, чтобы подключиться

	ssh user@localhost -p 9000

Учтите, что ВМ нужно время для запуска и сразу она не будет доступна для подключения!

Но, если следовать примерам, ни одной ВМ сейчас не запущенно, да и перенаправление будет в никуда, поэтому рекомендую сперва дочитать этот пункт

### Перенаправление

По умолчанию подключение направляется на ВМ с id 0

*Чтобы было куда подключаться создайте новую ВМ /vm post {}*

Чтобы изменит перенаправление подключения:

	/connect post
	{
		id = 1
	}

Теперь `ssh user@localhost -p 9000` должен работать

*пароль для `disk.qcow2` `P@ssw0rd`*

### Куда перенаправляет?

Чтобы узнать на какую ВМ сейчас перенаправляются запросы:

	/connect get
	{
	}

Получим примерно `1`

## Тестирование работы с образами дисков

Вы могли заметить, что уже есть один предустановленный диск `disk.qcow2`. Это базовый установленный `Alpine` для виртуализации

Отмечу, что это приложение поддерживает лишь формат дисков `.qcow2`

### Список

Чтобы получить список дисков:

	/disk get
	{
	}

Получите примерно:

	{
		"arr": [
			{
				"name": "disk.qcow2",
				"desc":"string"
			}
		]
	}

`desc` - описание диска

### Выгрузка

Чтобы выгрузить диск с сервера:

	/disk/download/disk.qcow2 get
	{
	}

Вместо `disk.qcow2` можно подставить любое другое имя диска, который Вы хотите выгрузить

Собственно, если используете `curl`, то нужно ещё указать куда его сохранить, т.е.

	curl localhost:8000/disk/download/disk.qcow2 --output disk.qcow2

### Загрузка

Чтобы загрузить диск на сервер:

	/disk post
	{
		name = "test.qcow2",
		desc = "test disk",
		file = "@disk.qcow2"
	}

`name` - новое имя диска на сервере, `desc` - его описание, а `file` - в `/docs`: будет предложено загрузить файл, а через `curl`: нужно указать путь, начав с `@`

### Удаление

Чтобы удалить диск с сервера:

	/disk delete
	{
		what = "test.qcow2"
	}

Учтите, что диск удаляется безвозвратно!

### Копирование

Диски на сервере можно и копировать:

	/disk/copy post
	{
		from_ = "disk.qcow2",
		to = "test.qcow2",
		new_desc = "test disk again"
	}

Учтите, что перезаписывать таким образом диски нельзя!

`from_` имеет `_` из-за ключевого слова в `python` ._.
